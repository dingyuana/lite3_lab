## 核心概念

### UDP 命令头

`lite3_common.py` 将 UDP 载荷开头定义为三个小端无符号 32 位整数：

| 字段 | 含义 |
|---|---|
| `code` | 命令码或上报帧码 |
| 第二个整数 | 简单命令中的 `value`；复杂命令中的 payload 字节长度 |
| `type` | 简单命令为 0；复杂命令默认为 1 |

`pack_simple()` 生成 12 字节载荷；`pack_complex()` 在 12 字节头后追加 payload。接收端只处理 `type=1` 的遥测帧；扬声器状态 `0x11050F08` 是 `type=0` 的特例。

UDP 本身没有应用层的“已执行”回执。`send()` 的发送计数增长只表示本机完成了一次 `sendto()` 调用；动作是否执行必须看后续状态与遥测。

### 常用命令码

以下值均来自公共模块，仅用于认识现有实现，不表示可以脱离状态机随意组合发送。

| 命令码 | 常量 | 本项目用途 |
|---|---|---|
| `0x21040001` | `CMD_HEARTBEAT` | 心跳保活，默认 5 Hz |
| `0x21010C05` | `CMD_HOME` | 归零 |
| `0x21010202` | `CMD_STAND_SIT` | 起立/趴下切换，由当前状态决定语义 |
| `0x21020C0E` | `CMD_SOFT_ESTOP` | 软急停 |
| `0x21010D06` | `CMD_MOVE_MODE` | 移动模式 |
| `0x21010D05` | `CMD_STAND_MODE` | 站立模式常量；本课程基础流程不单独演示 |
| `0x21010300` | `CMD_GAIT_LOW` | 平地低速步态 |
| `0x21010130` | `CMD_AXIS_FORWARD` | 前向轴 |
| `0x21010131` | `CMD_AXIS_LATERAL` | 侧向轴 |
| `0x21010135` | `CMD_AXIS_YAW` | 偏航轴 |
| `0x2101030D` | `CMD_SPEAKER` | 扬声器控制/查询 |

课堂统一使用低速步态。task10 虽提供其他步态选项，但不能把“界面能选”理解为“本实验已验证其安全性”。

### 状态帧与关节帧

- `0x0901`：`RobotStateUpload` 结构体，代码断言其 payload 为 **208 字节**。部分上报帧带 4 字节 `98` 前缀，总 payload 为 **212 字节**；解析时跳过前缀。两种格式都支持。
- `0x0902`：12 个关节角，`double` 类型，payload 为 **96 字节**。关节原始值为弧度，日志同时换算为度。
- 四膝索引为 `[2,5,8,11]`，对应左前、右前、左后、右后膝关节。
- 状态默认接收端口为 `43897`，控制目标默认端口为 `43893`。这些是项目默认值，不是对现场网络配置的证明。

状态结构中的超声波为前/后两个 `double` 值。任务读取的是机器人上报的米制距离；不能把某个读数当作侧向保护，也不能假设传感器永远返回有限正数。

### 状态三元组与关键姿态

| 三元组 | 含义 | 课堂判断 |
|---|---|---|
| `(98,0,0)` | 初始待机 | 尚未首次起立；不能作为站立或归零完成证据 |
| `(1,0,0)` | 趴下 | 归零/起立流程的起点之一 |
| `(4,0,0)` | 准备起立 | 过渡态，等待 |
| `(5,0,0)` | 正在起立 | 过渡态，只发心跳 |
| `(6,0,0)` | 力控站立、低速、静止 | task03 的稳定站立状态 |
| `(6,0,1)` | 力控站立、低速、踏步/扭动 | 可作为移动就绪姿态 |
| `(7,0,0)` | 正在趴下 | 避免重复发送趴下命令 |
| `(17,0,0)` | 回零 | 必须继续观察是否回到 `(1,0,0)` |
| `(8,0,0)` | 失控保护 | 停止实验，检查现场并报告教师 |

判据是组合条件：task03 稳定站立还要求四膝均值 60°～90°连续 3 s；移动就绪要求四膝均值 60°～130°；趴下辅助判据要求四膝均值大于 130°。这些阈值是项目代码中的实验判据，不是机器人额定硬件参数。

### 新鲜度、帧龄与“读取不会刷新数据”

`get_state(max_age=0.5)` 与 `get_joint(max_age=0.5)` 只返回最新一帧，且要求帧龄严格小于指定值；`state_age()` 返回最新状态帧的原始年龄。

因此：

- 多次读取旧帧不会让数据变新。
- `get_state()` 返回 `None` 可能表示从未收到，也可能表示已经超过 0.5 s。
- task12 必须用 `snapshot()["state_age"]` 更新声纳时间戳，不能把 `snapshot()` 调用时刻当作声纳采样时刻。
- 视觉帧使用 `VideoStream.latest_with_timestamp()` 返回的采集时间戳，不能用 GUI 每 50 ms 刷新一次的时刻冒充新帧。

### 轴流、死区与停车

移动准备完成后，脚本以默认 30 Hz 发送前向、侧向、偏航轴。轴值范围由公共映射限制在约 ±32767；死区常量为：

- 前向：6553。
- 侧向：12553。
- 偏航：9553。

task06/07/08 会拒绝小于或等于前向死区的 `--value`。task12 的 `twist_to_axis()` 会将落在死区内的小非零输出抬到死区外一单位，使后退和转向能够越过固件死区；零输入仍映射为零。

**正常停车顺序**：

1. 三个运动轴写入 `(0,0,0)`。
2. 维持零值轴流，同时观察 `vel_body[0]` 等遥测。
3. 确认速度低于实验阈值或进入收尾状态。
4. 需要结束实验时，再趴下并按任务要求归零。
5. 关闭客户端前再次确认没有残留按键、跟踪会话或轴流。

不要用“立即结束进程”代替停车。代码注释指出，轴指令停止约 250 ms 后底层可能接管，突然失去支撑。

### 三种“停止”不能混为一谈

| 方式 | 作用 | 使用场景与限制 |
|---|---|---|
| 运动轴归零 | 请求停止当前运动，保留控制链路 | 正常松开按键、目标丢失、切换步态前 |
| 软急停 `0x21020C0E` | 发送项目定义的软急停命令 | 异常时由安全员执行；不等于机械断电 |
| 人工扶稳/物理急停 | 从物理上阻止倒地、夹伤或碰撞 | 悬挂、护架、首次动作与紧急情况 |

软急停命令如下，应在另一终端待命，IP 按现场配置替换：

```bash
python3 -c "import lite3_common as l3,time; c=l3.Lite3Controller('192.168.1.120'); c.start_heartbeat(5); c.send_simple(l3.CMD_SOFT_ESTOP); time.sleep(1); c.close()"
```

若发生起火、冒烟、线缆破损、剧烈失控或人员受伤，优先按实验室规程切断电源并组织撤离，不依赖 UDP 命令。

## task12 安全逻辑速查

| 机制 | 当前代码判据 | 触发后的行为 |
|---|---|---|
| 视觉帧龄 | 无有效时间戳、负帧龄或帧龄大于 0.2 s | PID 清零、运动轴归零，提示视频帧过期/不可用 |
| 感知链路超时 | 距最近一次成功 tracker update 超过 0.5 s | `STOP` |
| 独立看门狗 | 距最近一次控制循环更新超过 1.0 s；每 0.05 s 检查 | 轴归零、退出跟踪状态（恢复手动可用）、结束跟踪会话 |
| 目标丢失 | 当前帧 tracker 返回 `None` | **立即停车**，不等待连续 10 帧 |
| 地面反投影 | 非有限坐标或前向距离不大于 0 | 立即停车 |
| 超声波帧龄 | 状态原始帧龄大于 0.3 s，或读数无效/不大于 0 | `STOP` |
| 视觉目标距离 | 小于 1.0 m 进入过近；大于 1.3 m 解除过近 | 过近只允许转向，不给前进轴 |
| 目标过远 | 大于 3.5 m 进入过远；小于 3.0 m 解除过远 | `STOP` |
| 额外前后防撞 | task10 控制器对前进入口再检查前方距离，对后退检查后方距离；阈值 1.0 m | 相应方向轴归零；跟踪时同时将偏航轴归零 |
| dummy 拦截 | 真机使用 `--dummy-h`、文件名含 dummy，或矩阵等于按当前画面尺寸生成的占位矩阵 | 拒绝启动，不发送跟踪运动命令 |

`SafetySupervisor` 中保留 `lost_confirm=10` 与 `lost_frames` 字段，但 `check()` 在 `target is None` 时直接返回 `STOP`；教学验收应以立即停车为准。

## 思考题

1. 为什么 UDP 发送计数不能作为起立、移动或归零成功的证据？
2. 212 字节 `0x0901` payload 与 208 字节 payload 的差别在哪里，为什么不能把 98 当成命令头 code？
3. `get_state()` 返回 `None` 有哪两种可能？应如何区分？
4. 为什么停车后不能立刻停止轴流？正常停车与软急停的目标有何不同？
5. 为什么左右移动没有前后超声波保护？实验场地应怎样调整？
6. task12 的视觉帧龄为什么使用采集时间戳，而不是 GUI 显示时间戳？
7. 如果声纳数值一直很大但状态帧已经超过 0.3 s，跟随应继续还是停车？为什么？
8. 为什么 PID 数值自检通过后，仍必须做真机偏航符号验证？

## 常见错误

| 现象/错误 | 可能原因 | 处理与预防 |
|---|---|---|
| 一直显示“无状态” | 上报目标未配置、防火墙、状态端口占用、机器人未上报 | 先查路由与端口，不连续发送运动命令试探 |
| 收到 ICMP 端口不可达 | 对端控制端口无进程监听或网络路径异常 | 停止运动实验，核对 IP、供电和运控程序 |
| 将 98 显示为连接错误 | 混淆了状态 payload 字段与命令头 code | 按初始待机解释，等待首次起立 |
| 起立后立刻发送轴值 | 把站立完成与移动准备混为一谈 | 先切移动模式、启动零轴流、再切低速步态并确认 |
| 用旧声纳值判断安全 | 读取调用刷新了“看起来的时间” | 使用原始 `state_age`，超过阈值停车 |
| 把 task06 的“~方向正确”当作全通过 | task06 即使未停稳也可能返回 True | 教师验收必须单独核对停车日志 |
| 认为软急停万无一失 | UDP 故障时命令可能无法送达 | 保留机械/人工防护和物理断电方案 |
| 为验证方向而快速连续换向 | 惯性叠加、第二个控制源干扰 | 每段后轴归零并等待，保持足够场地 |
| 把 target 丢失阈值背成 10 帧 | 沿用了类中保留字段 | 以 `check()` 立即 `STOP` 的实际逻辑为准 |
