# Lite3 实训考核与故障排查

## 学习目标

完成本单元后，学生应能够：

1. 按统一标准完成环境、物理、双引擎、强化学习和 ROS2/LiDAR 实验验收。
2. 用最小测试和日志证据定位故障，避免无依据地修改模型、策略或源码。
3. 识别资源路径、图形界面、观测顺序、执行器接口和话题通信中的高频问题。
4. 对 stage3 的 45 维观测、默认角、PD 力矩和 0.5 秒超时作出准确解释。
5. 对 stage5 的数据来源和算法边界作出明确说明。
6. 形成包含运行条件、操作步骤、观察证据、结论和局限性的实训记录。

## 建议学时

建议 **2 学时**：1 学时综合排查与考核说明，1 学时现场验收与答辩。课外完成实验记录整理。

| 活动 | 学时 |

- 已完成 stage1～stage5 的基本操作。

## 核心概念

### 证据优先的排查方法

推荐按以下顺序排查：

```text
确认脚本与运行目录
→ 确认模型/策略资源
→ 确认 Python/ROS2 环境
→ 确认 GUI/TTY/焦点
→ 确认状态与控制量
→ 确认话题、频率与时间戳
→ 最后才考虑修改参数或代码
```

每次只改变一个变量。先保存原始日志，再复位和重试。没有日志的“机器人不动”无法区分模型未加载、控制量为零、话题断开还是超时保护。

### 必须掌握的四个量化检查点

| 检查点 | 正确结果 |
|---|---|
| 水平机身重力投影 | `[0,0,-1]` |
| x 轴 `+90°` 重力投影 | `[0,-1,0]` |
| stage3 默认角 | `[0,-0.65,1.3]` 重复 4 次 |
| PD 样例及限幅 | 未限幅 `[13,-26]`；`[-5,10]` 限幅后 `[10,-5]` |

此外，stage3 观测必须是 `float32` 的 `(45,)` 数组，ROS2 仿真在超过 0.5 秒没有有效关节命令时必须输出零力矩。

### 安全停止与故障保护不是同一件事

- 键盘空格：主动发送零速度命令。
- 键盘 1 秒无输入：主动把键盘速度命令清零并继续发布。
- 仿真器 0.5 秒无有效 `/JOINTS_CMD`：被动输出零力矩。
- `r`：恢复部分仿真状态，但 stage3 的速度命令不会自动清零。

因此，正确习惯是“先停车，再复位；先结束发布者，再检查超时”。

## 教师演示

### 演示 1：无 GUI 预检

```bash
cd ~/lite3_lab/simulation
source .venv/bin/activate
python3 -m unittest discover -s tests -v
```

随后检查资源：

```bash
ls ../Lite3_rl_deploy/third_party/deep_robotics_model/Lite3/Lite3_urdf/urdf/Lite3.urdf
ls ../Lite3_rl_deploy/third_party/deep_robotics_model/Lite3/Lite3_mjcf/mjcf/Lite3.xml
ls ../Lite3_rl_deploy/policy/ppo/policy.onnx
```

本组测试不打开仿真窗口。如果测试通过而 GUI 启动失败，应优先排查图形显示，而不是重写观测或 PD 代码。

### 演示 2：ROS2 分层预检

每个 ROS2 终端先执行：

```bash
source /opt/ros/<发行版>/setup.bash
source <工作空间>/install/setup.bash
python3 -c "import rclpy; import drdds.msg; print('ROS2 and drdds OK')"
```

再启动仿真与一个控制器，检查：

```bash
ros2 topic list
ros2 topic info /cmd_vel --verbose
ros2 topic info /JOINTS_CMD --verbose
ros2 topic hz /JOINTS_DATA
```

教师应现场展示“缺少 source”“没有订阅者”“两个发布者”三种故障的不同证据。

### 演示 3：关键故障定位

故意选择只读方式复现：

- 从错误目录运行脚本，展示导入/资源路径问题；
- 不启动发布者，展示 0.5 秒零力矩；
- 启动键盘但不启动步态节点，展示“没有 `/cmd_vel` 订阅者”；
- 只启动 stage5，说明它不会自动接收 stage4 键盘命令。

不修改课程源码，不伪造通过结果。

## 学生实操

### 综合验收任务

1. **环境与资源**：记录 Python 及主要包版本，确认三个资源文件存在。
2. **基础测试**：运行 6 项单元测试，解释重力投影、默认角、PD 和观测测试。
3. **双引擎**：分别完成 stage1 站立/trot/推力/复位和 stage2 站立/蹲伏/环境切换/复位。
4. **本地策略**：运行 stage3，演示 `x→r`、速度命令、转向、停止和侧向扰动。
5. **ROS2 链路**：串行运行 stage3 仿真、一个 stage4 转换节点和键盘节点，检查话题反馈。
6. **超时保护**：停止关节命令发布者，确认超过 0.5 秒后零力矩。
7. **LiDAR 前端**：运行 stage5，检查点云、真值里程计、TF 和 Marker。
8. **边界答辩**：明确说明 stage5 没有建图、定位、扫描匹配或回环。

### 实训记录最小内容

每次实验至少记录：

- 脚本名和运行目录；
- WSL/ROS2/虚拟环境状态；
- 初始姿态、摩擦、重力和命令；
- 实际操作与时间顺序；
- 关键日志或话题输出；
- 观察结果及证据；
- 复位/停止操作；
- 结论、可能原因和未验证因素。

### 现场抽查询问

教师随机抽取以下问题，学生需口头回答并指向代码或测试证据：

1. 45 维观测每一段是什么？
2. 为什么使用 `R^T`？
3. 默认角为何是 `(0,-0.65,1.3)`？
4. 为什么 `data.ctrl` 不能接收目标角？
5. 无效 ROS2 指令会不会刷新超时时间？
6. stage4 两个转换节点为何不能同时运行？
7. stage5 的里程计是真值还是 SLAM 估计？

## 思考题

1. 单元测试全部通过，是否足以证明 GUI、ONNX 模型和 ROS2 环境都正常？为什么？
2. 如果观测长度是 45 但顺序错误，测试或日志会怎样提示？部署前应如何避免？
3. 如果机器人摔倒后按 `r` 仍继续前进，可能漏掉了哪一步？
4. 如果 ROS2 仿真收到非法消息后仍使用旧力矩，是否说明校验失效？
5. 为什么“有发布者”不代表“有订阅者”，也不代表“消息频率足够”？
6. 如果外部 SLAM 无法直接消费 stage5 的点云，可以从哪些坐标系/时间信息入手检查？
7. 真值轨迹完全平滑是否能够证明外部 SLAM 实现正确？
8. 为什么排障时应先复位和保存日志，而不是连续叠加推力、重力和低摩擦？

## 验收标准

### 合格线与一票否决项

总评达到 **60 分** 为合格，并须同时满足以下条件：

- 能正确说明 45 维观测顺序；
- 能正确说明 `R^T*(0,0,-1)`；

## 常见错误与故障排查

### 启动与资源问题

| 现象 | 可能原因 | 排查与处理 |
|---|---|---|
| `README` 命令可读但模型文件不存在 | 只复制了 `simulation` | 恢复同级 `Lite3_rl_deploy` 目录结构 |
| `ModuleNotFoundError: project_paths` | 未从脚本目录运行，或工作目录错误 | 回到 `~/lite3_lab/simulation` 再启动 |
| ONNX 文件不存在 | 策略资源未随项目迁移 | 检查 `project_paths.py` 指向的 `policy/ppo/policy.onnx` |
| PyBullet/MuJoCo 导入失败 | 未激活虚拟环境或包未安装 | `source .venv/bin/activate`，检查 `pip install -r requirements.txt` |
| `rclpy`/`drdds` 导入失败 | 未 source ROS2 或消息工作空间 | 每个终端重新 source 两个 setup |
| GUI 无法打开 | WSLg、`DISPLAY` 或显卡显示异常 | 先在 WSL 内检查图形环境；不要先改控制代码 |
| 键盘脚本报 TTY 错误 | 通过非交互式管道或后台方式启动 | 使用交互式 WSL 终端，不要用 `nohup` 代替键盘输入 |

### stage1/stage2 操作问题

| 现象 | 可能原因 | 排查与处理 |
|---|---|---|
| stage1 方向键无效 | PyBullet 窗口没有焦点 | 点击查看器窗口后再按方向键 |
| stage1 数字键无效 | 实际运行的是 stage2 | 核对脚本和键位表 |
| stage2 输入无反应 | 终端输入未回车，或输入焦点不在查看器 | 终端字母后回车；查看器字母直接按键 |
| stage2 多个命令“只执行一个” | 短时间堆积多个队列项 | 主循环每步取一个，逐条输入并观察 |
| 接触对数为 0 但模型已加载 | 机器人离地、零重力或已翻倒 | 结合高度、姿态和模式判断，先复位 |
| 零重力后仍继续运动 | 零重力不清除已有速度 | 按 `r` 或等待耗散，不要误判为重力未生效 |
| 复位后仍前进/受力 | 忽略模式、摩擦、推力或速度命令状态 | 阅读对应脚本的复位范围；stage3 先 `x` 再 `r` |

### stage3 策略与力矩问题

| 现象 | 可能原因 | 排查与处理 |
|---|---|---|
| 策略输入维度报错 | ONNX 输入不是 45 维 | 核对模型与脚本是否配套，不随意改 `OBS_DIM` |
| 行为异常但无异常日志 | 观测顺序、缩放或默认角错误 | 对照 45 维表和 6 项单元测试 |
| 重力方向看起来相反 | 使用了 `R` 而非 `R^T`，或四元数顺序错误 | 验证水平与 x 轴 `+90°` 两个测试 |
| 机器人像被“角度数值”驱动 | 把目标角直接写入 `data.ctrl` | 恢复 PD 力矩计算与限幅 |
| 站立高度不稳定 | 使用其他阶段默认角或增益 | stage3 使用 `(0,-0.65,1.3)`、`kp=30`、`kd=1` |
| 按 `r` 后仍前进 | `r` 不清速度命令 | 先 `x` 再 `r` |
| 动作看似没有效果 | 关注了原始动作而非目标角/力矩 | 检查 `default+0.25*action` 和 `data.ctrl` |
| 离线测试通过但 GUI 失败 | MuJoCo/ONNX 运行环境或模型问题 | 分开验证 Python 包、资源、GUI 和 ONNX |

### ROS2 通信问题

| 现象 | 可能原因 | 排查与处理 |
|---|---|---|
| `ros2` 命令找不到 | ROS2 未安装或未 source | 检查安装和当前终端 setup |
| 话题列表为空/缺少预期话题 | 节点未启动、域名不同或提前退出 | 检查进程日志、`ROS_DOMAIN_ID` 和节点状态 |
| 键盘提示无 `/cmd_vel` 订阅者 | 步态转换节点未启动 | 启动 `walk_sim` 或 `controller` 之一 |
| 机器人收到两套交错步态 | 两个 stage4 转换节点同时运行 | 只保留一个 `/JOINTS_CMD` 发布者 |
| 停止键盘后仍运动 | 转换节点保留最后 `/cmd_vel` | 先按空格，再结束节点 |
| 仿真收到命令仍拒绝 | 关节数不为 12、无法解析或含 NaN/Inf | 查看警告，修正消息；非法消息不会保活 |
| 关节状态不更新 | 仿真未运行或进程异常 | 检查 MuJoCo 日志和 `/JOINTS_DATA` 频率 |
| 发布者停止后机器人下沉 | 0.5 秒超时主动输出零力矩 | 这是设计行为，不是通信“卡死”；先复位 |
| 命令看似安全但力矩过大 | 有限值校验不等于幅值限幅 | 教师监督下使用合理增益/力矩；当前 ROS2 路径无自动限幅 |

### stage5 与数据前端问题

| 现象 | 可能原因 | 排查与处理 |
|---|---|---|
| stage5 不响应 stage4 键盘 | 两者没有控制连接 | stage5 使用自身窗口和内部键盘状态 |
| `/lidar_points` 没有消息 | 没有有效命中、节点未发布或未运行 | 检查进程、世界系点云和 `0<dist<15 m` 条件 |
| 点云数量不是 144 | 144 是射线方向上限，不是保证点数 | 只有有效命中才生成点 |
| 真值轨迹不变 | 机器人没有移动或仿真未推进 | 在 stage5 查看器按 `w/s/a/d`，检查内部 `vx/wz` |
| TF 找不到 | 未 source TF 包、节点未发布或帧名错误 | 检查 `world` 和 `base_link`，使用 `tf2_echo` |
| 外部 SLAM 无法直接使用点云 | 世界系、时间戳、传感器外参或 `/clock` 不匹配 | 先确认输入约定；当前脚本不提供完整 SLAM 集成 |
| 期待地图却看不到 | 课程脚本没有建图模块 | 正确结论是“stage5 只是数据前端” |
| 把 `/ground_truth_odom` 当作估计 | 混淆真值与 SLAM 输出 | 检查代码来源：直接读取 MuJoCo `qpos` |

### 需要升级给教师的情况

出现以下情况应停止实验并报告教师，而不是继续加大推力或增益：

- 模型能加载但持续穿透地面或出现极端数值；
- ONNX 输入维度与 45 不符；
- ROS2 消息中的 NaN/Inf 无法定位来源；
- 有效命令在超时后仍出现异常大力矩；
- 多发布者导致控制交错且无法确认唯一发布者；
- WSL 图形环境或 ROS2 工作空间被破坏，需要系统级修复。

## 常见错误

- **只背命令，不检查运行目录和环境**：同一句命令在不同终端可能得到不同结果。
- **把测试通过等同于所有实验通过**：单元测试不覆盖 GUI、完整 ONNX 推理和 ROS2 通信。
- **同时改变摩擦、重力和姿态**：无法归因，实验结果不可复核。
- **将设定速度当作真实测量速度**：日志字段必须结合代码来源解释。
- **用真值里程计冒充 SLAM 估计**：违反课程边界，也不能用于证明算法效果。
- **忽略非法消息不刷新时间戳**：会误判 0.5 秒超时行为。
- **将零力矩理解为安全站姿**：它只是停止主动施力，重力仍可能使机器人倒下。
- **在没有保存日志前反复重启**：丢失故障现场，导致无法比较。
- **直接修改课程源码来“修环境”**：应优先恢复依赖、资源、工作空间和 source 顺序。
- **验收记录只写截图不写条件**：至少应记录脚本、初始状态、改变量和复位步骤。
