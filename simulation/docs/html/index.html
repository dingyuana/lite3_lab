Lite3 大学生实训项目仿真课程导学

课程定位与使用方式

本课程以 ~/lite3_lab/simulation 中的 Lite3 四足机器人仿真代码为主线，按照“物理基础 → 双引擎实验 → 强化学习部署 → ROS2 控制 → LiDAR 数据前端 → 综合考核”的顺序展开。课程只使用仿真环境，不连接真实机器人。

Windows 可通过 \\wsl.localhost\<发行版>\home\<用户>\lite3_lab\simulation 访问同一目录，但 PyBullet、MuJoCo、ONNX Runtime 和 ROS2 实验应在 WSL 中运行。ROS2 实验需先 source 对应发行版及 drdds 消息包所在的工作空间；pip install -r requirements.txt 不能替代 ROS2 安装。

学习目标

完成课程后，学生应能够：

核心概念

从模型到执行的完整链路

每章都围绕同一条链路检查问题：

模型文件 → 仿真状态 → 观测/控制器 → 策略或目标姿态 → 执行器力矩 → 下一仿真状态

例如 stage3 中，模型状态先构造 45 维观测，ONNX 输出 12 维动作；动作用于生成目标关节角，再由 PD 公式转成 12 维力矩，最后写入 data.ctrl。任何一层使用了错误的坐标、关节顺序或单位，后一层即使代码“能运行”，结果也会错误。

资源定位与项目边界

project_paths.py 以该文件自身位置为基准向上找到项目根目录，并定位：

  • URDF：Lite3_rl_deploy/third_party/deep_robotics_model/Lite3/Lite3_urdf/urdf/Lite3.urdf
  • MJCF：Lite3_rl_deploy/third_party/deep_robotics_model/Lite3/Lite3_mjcf/mjcf/Lite3.xml
  • ONNX：Lite3_rl_deploy/policy/ppo/policy.onnx

因此，模型和策略应位于 simulation 的同级项目目录中。assets/generated/ 是历史生成文件，不参与课程运行。复制脚本时不要只复制 .py 文件而丢失同级模型目录。

核心概念

模型文件与仿真循环

URDF 主要描述机器人连杆、关节、惯量、碰撞与视觉几何；MJCF 是 MuJoCo 使用的模型描述格式。本课程通过 project_paths.py 分别加载：

  • PyBullet：Lite3.urdf
  • MuJoCo：Lite3.xml

模型文件不会告诉控制器“此刻应该怎么走”。每个仿真循环通常包括：

读取状态 → 计算控制量 → 写入执行器 → 推进一个时间步 → 更新接触与运动状态

因此，研究控制效果时必须同时检查“状态读取”和“执行器写入”，不能只看策略或步态函数。

世界系、机体系与四元数

本课程约定世界系竖直向上为 +z，重力方向向量为 (0,0,-1)。四元数按 MuJoCo 的顺序 (w,x,y,z) 排列。

设 R(q) 将机体系向量转换到世界系：

v_world = R(q) · v_body

若已知世界系中的方向，需要计算机体系中的表示，就使用逆变换。旋转矩阵的逆等于转置：

v_body = R(q)^T · v_world

策略需要的不是以 m/s² 为单位的重力大小，而是重力的单位方向在机体系中的投影，所以：

g_body = R^T · (0,0,-1)

R^T*(0,0,-1) 的物理意义

stage3_mujoco_rl.py 中的 projected_gravity() 根据 (w,x,y,z) 四元数构造机体系到世界系的旋转矩阵，再执行 rotation.T @ GRAVITY_DIRECTION。

机身姿态世界重力方向机体系投影含义
水平，单位四元数 [1,0,0,0](0,0,-1)(0,0,-1)重力从脚底方向向下作用
绕世界/机身 x 轴旋转 +90°(0,0,-1)(0,-1,0)机体系 -y 方向朝向重力

第二个结果正是 tests/test_stage3_rl.py 验证的 [0,-1,0]。如果误写成 R*(0,0,-1)，表示的已经是世界系方向，不能直接作为机体系观测；在非单位姿态下，它与正确答案一般不同。

投影向量的长度在数值精确时应为 1。它可以随姿态改变三个分量，但不随重力加速度数值 9.81 改变。

Lite3 状态数组布局

本课程的 Lite3 模型具有自由浮动机身，随后是 12 个驱动关节。理解以下布局是排查观测错误的前提：

数组范围内容
data.qpos[0:3]0、1、2机身位置 x,y,z
data.qpos[3:7]3、4、5、6机身四元数 w,x,y,z
data.qpos[7:19]7～1812 个关节位置
data.qvel[0:3]0、1、2stage3 使用的机身角速度分量

stage3 不直接假设所有关节一定从固定下标开始，而是通过 model.actuator_trnid 找到每个执行器对应的关节，再用 model.jnt_qposadr 与 model.jnt_dofadr 得到地址。这样可以把关节位置和速度稳定地组织成 12 维数组。

这些下标对应当前 Lite3 自由关节模型。若换成固定底座、不同关节数或不同模型，必须先重新检查布局，不能机械照搬。

关节顺序与默认关节角

stage3 的默认位置由 np.tile([0.0,-0.65,1.3],4) 生成，即每三个关节为一组：

[HipX, HipY, Knee] × 4

结合 stage4 的编号约定，四组依次为 FL、FR、HL、HR。stage3 实际读取时仍以模型执行器顺序为准。默认角表示“每个策略动作围绕哪个姿态变化”，不是“机器人实际已经达到的关节角”。

PD 力矩与执行器接口

PD 力矩的基本形式为：

tau = kp * (q_target - q) + kd * (q_velocity_target - q_velocity)

stage3 的关节速度目标为 0，因此：

tau = 30 * (q_target - q) + 1 * (0 - q_velocity)
   = 30 * (q_target - q) - q_velocity
  • 位置误差越大，比例项产生的恢复力矩越大。
  • 关节速度越大，微分项越倾向于抑制运动。
  • 最终力矩还要按 model.actuator_ctrlrange 的每个执行器上下限裁剪。

例如测试输入 q_target=[1,-1]、q=[0.5,0]、q_vel=[2,-4]：

tau[0] = 30*(1-0.5) - 2 = 13
tau[1] = 30*(-1-0) - (-4) = -26

若每个执行器限幅为 [-5,10]，结果应为 [10,-5]。

位置目标不等于力矩

Lite3.xml 中 stage3 使用的执行器是电机，data.ctrl 接收的是力矩。因此正确的链路是：

ONNX 动作 → 目标关节角 → PD 计算 → 电机力矩 → data.ctrl

如果跳过 PD，把 12 个目标角直接写入 data.ctrl，解释器的数值可能仍然合法，但执行器会把角度数值当作力矩，导致行为完全错误。

相比之下：

  • stage1 使用 PyBullet 的 POSITION_CONTROL 接口，由仿真器结合电机参数跟踪目标位置。
  • stage2 在代码中显式计算 40*(target-qpos)-2*qvel，再写入 data.ctrl。
  • stage4/stage5 也显式或间接使用 kp=40、kd=2 的位置反馈生成关节指令/力矩。

时间步、频率与外力的区别

  • DT=1/240 是 stage1 的仿真步长；trot 频率 2.0 Hz 是步态参数，两者不是同一个概念。
  • 控制频率决定多久重新计算一次指令；仿真步长决定积分器多久推进一次物理状态。
  • stage1 的 150 N 推力每步乘 0.95 衰减，属于逐渐减弱的持续外力。
  • stage2 的 150 N 推力持续 0.15 s，按模型时间步折算为若干仿真步。
  • stage3 的侧向 150 N 触发后在后续步中按 0.9 衰减。

因此，“都按了 p”不代表三个实验受到相同冲量或相同扰动。

常见错误

  • 把投影重力乘以 9.81 后送入观测：当前策略需要单位方向，测试也按单位方向验证。
  • 关节位置和关节速度使用同一组下标：qpos[7:19] 与 qvel[6:18] 的起始下标不同。
  • 用 qpos[:12] 取关节角：会混入机身位置、四元数和部分关节数据。
  • 把默认角当作实际反馈：默认角是策略动作中心；反馈来自当前 qpos。
  • 认为 PD 能无限产生力矩：实际执行器有控制范围，超限部分会被裁剪。
  • 忽略外力施加时间：stage1 衰减、stage2 持续 0.15 秒、stage3 单步触发后衰减，三者不同。

stage1 的四种行为

  1. 站立：按基础站姿下发位置目标；站立/trot 的最大电机力参数为 60。
  2. trot：频率 2.0 Hz，FL 与 HR 同相，FR 与 HL 反相；运动时还会施加沿机身 x 轴、大小为 30*|vx| 的辅助外力。
  3. 阻尼：使用 VELOCITY_CONTROL，目标速度为 0，力参数仅 0.1，用于被动耗散运动。
  4. 安全蹲伏：HipY=-1.5、Knee=2.6，最大力参数为 30，通过降低姿态增强稳定性。

trot 的膝关节抬腿量为：

0.30 * max(0, -sin(phase))

HipY 在基础角上叠加 0.25*sin(phase) 和 0.2*vx。这是一种脚本式开环步态，不使用状态反馈重新规划落足点。

摩擦、重力与接触

  • 摩擦系数影响接触处抵抗相对滑动的能力，低摩擦不直接改变重力方向。
  • 零重力消除了维持站立所需的主要载荷，但不会自动把速度、位置或关节角清零。
  • 接触对数是接触约束数量，不是“几只脚稳稳着地”的直接计数。
  • 机器人发生摔倒后，单纯等待不会恢复站姿；应先按 r 再开始下一组对照。

核心概念

部署链路与控制周期

stage3_mujoco_rl.py 每个仿真步执行以下链路：

读取 qpos/qvel
  → 计算机体系投影重力
  → 拼接 45 维观测
  → ONNX 输出 12 维动作
  → target = default + 0.25 * action
  → tau = PD(target, qpos, qvel) 并按执行器范围限幅
  → data.ctrl = tau
  → mj_step

策略通过 ONNX Runtime 的 CPUExecutionProvider 运行。脚本读取 ONNX 输入维度，若不是 45 会直接报错，避免在错误输入形状下继续推理。

45 维观测的精确顺序

build_observation() 按以下顺序拼接，最终类型为 float32、形状为 (45,)：

切片索引内容维数缩放/处理
obs[0:3]机身角速度3乘以 0.25
obs[3:6]机体系投影重力3不缩放
obs[6:9]速度指令 [vx,vy,vaw]3不缩放
obs[9:21]关节位置偏差 q-default12不缩放
obs[21:33]关节速度12乘以 0.05
obs[33:45]上一帧动作12不缩放

维度合计：

3 + 3 + 3 + 12 + 12 + 12 = 45

“上一帧动作”指上一轮 ONNX 输出的原始动作，不是目标角，也不是已经限幅的力矩。初始化与复位时该数组为 12 维零向量；当前帧先构造观测，推理返回后才把 action 更新为新结果。

各段长度由 expected_sizes=(3,3,3,12,12,12) 检查。即使总长度碰巧为 45，只要某一段长度错误，也应视为观测构造错误。

投影重力：R^T*(0,0,-1)

策略不能直接读取“世界系重力”，而需要知道重力相对机身的方向。设 R 是机体系到世界系的旋转矩阵，则：

g_body = R^T * g_world_direction = R^T * (0,0,-1)

两个必须掌握的结果：

  • 机身水平、四元数为 [1,0,0,0] 时，g_body=[0,0,-1]。
  • 绕 x 轴 +90°、四元数为 [sqrt(0.5),sqrt(0.5),0,0] 时，g_body=[0,-1,0]。

它让策略在身体侧倾、俯仰或翻滚时获得姿态相关信号。投影重力只是姿态线索之一，不能单独代替完整状态。

默认关节角与动作缩放

部署策略的默认模式为：

DEFAULT_JOINT_PATTERN = [0.0, -0.65, 1.3]  # HipX, HipY, Knee
default_qpos = [0.0,-0.65,1.3] × 4

结合 stage4 的编号约定，四组为 FL、FR、HL、HR；stage3 的实际读取仍由模型执行器与关节地址决定。动作与目标位置的关系为：

target_qpos = default_qpos + ACTION_SCALE * action
ACTION_SCALE = 0.25

例如默认角为 -0.65、策略输出该关节动作为 0.4，则目标角为：

-0.65 + 0.25*0.4 = -0.55

这不是把实际关节角增加 0.4，也不是直接令电机输出 0.4 N·m。

不能使用 stage1/stage4 的 HipY=-0.985、Knee=2.084 替换 stage3 的部署默认角。策略的观测偏差和动作中心都建立在 (0,-0.65,1.3) 上。

PD 力矩，而不是目标角度

Lite3.xml 的执行器是电机，stage3 的 data.ctrl 需要力矩：

tau = 30*(target_qpos-qpos) + 1*(0-qvel)

随后按每个执行器的 model.actuator_ctrlrange 逐元素裁剪。

ROS2 仿真：消息、校验与 MIT 力矩

stage3_mujoco_ros2_sim.py 提供：

  • 订阅 /JOINTS_CMD，消息类型为 drdds.msg.JointsDataCmd。
  • 发布 /JOINTS_DATA，消息类型为 drdds.msg.JointsData。
  • 每个关节指令字段顺序为 [kp,kd,position,velocity,torque]。

接收端依次检查：

  1. len(joints_data) == model.nu，当前应为 12；
  2. 能转换为 float64 数值矩阵；
  3. 所有字段都是有限值，即不含 NaN 或 Inf。

只有全部通过，才在锁保护下替换命令并更新时间戳。无效指令不会覆盖上一条有效指令，也不会刷新时间戳。

有效命令下发的力矩为：

tau = kp*(position-q) + kd*(velocity-dq) + torque

这与本地 stage3 固定 kp=30、kd=1、速度目标为 0 的路径不同；ROS2 仿真允许命令携带增益、位置目标、速度目标和前馈力矩。

当前代码只校验“关节数量、可解析性、有限值”，不校验增益、位置、速度或力矩是否超出安全幅值；ROS2 路径也没有调用本地 pd_torque_control() 的 ctrlrange 限幅。有限值合法不等于控制安全。

0.5 秒超时与状态发布

仿真器使用 time.monotonic() 记录最近一次有效命令时间：

elapsed = now - last_valid_command_time
若 elapsed > 0.5 s：tau = 全零
否则：按 MIT 公式计算 tau
  • 节点启动时就初始化时间戳，因此即使从未收到命令，也会在约 0.5 秒后进入零力矩状态。
  • 正好等于 0.5 秒不必然触发，代码条件是严格大于 0.5。
  • 无效消息持续到达不能“保活”；时间戳只对有效消息更新。
  • 发布者停止后，最后一帧力矩最多被保持到超时判定，然后输出零力矩。
  • /JOINTS_DATA 每 5 个仿真步发布一次，包含 12 个关节的位置和速度；主循环每次睡眠约 0.002 s。

零力矩是安全失效保护，不会让机器人自动恢复默认站姿；在重力作用下机器人可能下沉或摔倒。

常见错误

  • 把观测段顺序写错但只检查总长度：ONNX 可能仍接受输入，但策略语义完全错误。
  • 把角速度或关节速度的缩放漏掉：分别是 0.25 和 0.05。
  • 把动作当作已经乘过 0.25：目标角计算时才乘动作缩放。
  • 沿用 stage1/2 的默认角：stage3 固定使用 (0,-0.65,1.3)。
  • 把 target_qpos 直接写入 data.ctrl：该执行器需要力矩。
  • 只写比例项、漏掉速度阻尼：会改变动态响应并可能导致振荡。
  • 误以为 r 会清除速度命令：应先 x 再 r。
  • 用 stage3_ros2_node.py 启动实验：文件整体被注释，没有有效运行入口。
  • 把非法消息到达当作“仍在线”：只有有效命令更新时间戳。
  • 把 0.5 秒超时理解为固定关闭电机电源：代码是在仿真主循环输出全零力矩。
  • 认为有限值检查就是安全限幅：当前 ROS2 路径没有幅值检查和 ctrlrange 裁剪。
  • 忽略 ROS2 source：rclpy 或 drdds 导入失败通常与工作空间环境有关，不应修改课程脚本绕过。

stage4 控制链

键盘节点 stage4_ros2_keyboard.py
    │ Twist, /cmd_vel
    ▼
步态转换节点（walk_sim 或 controller 二选一）

    ▼

每个节点有独立职责：

  • 键盘节点只生成速度命令；
  • 步态转换节点把速度命令转换为 12 个关节的 MIT 参数；
  • 仿真节点校验并执行关节指令，同时发布关节状态。

stage4 的频率与停止语义

组件周期注意事项

键盘的 1 秒自动停车与仿真器的 0.5 秒超时是两个不同机制：

  • 前者让键盘在无输入后持续发布零 /cmd_vel；
  • 后者让仿真器在没有新的有效 /JOINTS_CMD 时输出零力矩。

如果直接杀掉键盘进程，步态转换节点可能保留最后收到的 /cmd_vel 并继续发布关节命令。因此安全停止应先按空格，再结束进程；不要只关闭键盘终端。

ROS2 关节指令校验回顾

stage3_mujoco_ros2_sim.py 只接受：

  1. 恰好 model.nu 个关节，当前为 12；
  2. 能解析为数值的 [kp,kd,position,velocity,torque]；
  3. 所有数值均有限。

有效命令的力矩为：

tau = kp*(position-q) + kd*(velocity-dq) + torque

无效消息被拒绝且不更新时间戳。超过 0.5 秒没有新的有效消息时，仿真器输出 12 维全零力矩。

stage5 的节点边界

stage5_lidar_frontend_sim.py 是独立的 MuJoCo + ROS2 数据前端：

  • 它不订阅 /cmd_vel 或 /JOINTS_CMD；
  • 键盘 w/s/a/d/空格 在节点内部直接设置 vx/wz；
  • 它自行计算 12 关节 PD 力矩，kp=40、kd=2；
  • 它不调用 ONNX，也不运行 stage4 的步态转换节点。

因此，在 stage5 中启动键盘遥控或 stage4 控制器不会形成预期控制链。stage5 的键盘速度大小为 0.3，与 stage4 键盘的 0.5 也不同。

理想 LiDAR 点云如何生成

每次发布时，节点：

  1. 以机身位置上方 0.2 m 为雷达原点；
  2. 用机身四元数把局部射线方向旋转到世界系；
  3. 在 4 个垂直角 [-15°,-5°,5°,15°] 与 36 个水平角 [0°,10°,…,350°] 上发射射线；
  4. 使用 mujoco.mj_ray 求首个命中距离；
  5. 只保留 0 < distance < 15 m 的命中点；
  6. 打包为 world 系的 PointCloud2。

理想情况下最多有 4×36=144 条射线方向，但只有发生有效命中的方向才产生点。若当前没有点，节点不会发布空点云消息。噪声代码处于注释状态，默认没有模拟运动畸变或随机噪声。

点云表达为世界系坐标，点云消息本身不携带雷达安装外参。若接入期望 lidar 或 sensor_frame 坐标的外部系统，需要额外提供坐标变换，这已超出当前脚本范围。

发布节奏与课程边界

主循环每次睡眠约 0.002 s，每 50 步发布一次点云、里程计、TF 和 Marker。若模型时间步为 0.002 s，名义频率约为 10 Hz，但实际间隔还受运行负载影响。

必须明确：

stage5 不是 SLAM。它只模拟 LiDAR 数据前端，并发布仿真真值里程计和 TF；不建立地图、不做定位、不做扫描匹配、不构建位姿图、不做回环，也不发布 SLAM 估计轨迹。

真值数据可用于外部 SLAM 的输入、可视化和误差评测，但不能把 /ground_truth_odom 当作算法输出。

常见错误

  • 忘记在每个终端 source ROS2：新终端不会自动继承另一个终端的环境。
  • 把 requirements.txt 当作 ROS2 消息包安装方式：drdds 等需要工作空间构建与 source。
  • 同时启动两个 stage4 转换节点：同一 /JOINTS_CMD 出现多发布者，步态交错。
  • 在 stage4 键盘输入后按回车等待：键盘使用单字符读取，不需要回车。
  • 非交互式终端启动键盘或 stage5：isatty、termios 或 tty 可能失败。
  • 只关闭键盘终端就以为停车：转换节点可能保留最后速度；应先按空格。
  • 期望 stage5 接收 /cmd_vel：stage5 使用自己的内部键盘状态和 PD 步态。
  • 把真值 TF 当作 SLAM 估计轨迹：它直接来自 MuJoCo qpos。
  • 把 stage5 称为完整 SLAM：当前没有地图、定位、扫描匹配或回环模块。
  • 点云没有消息就认定雷达故障：可能只是所有射线都未获得 0<dist<15 m 的有效命中。
  • 忽略点云为 world 系：外部 SLAM 若使用其他传感器系，需要额外坐标适配。
  • 忽略缺少 /clock 与雷达安装变换：当前脚本没有提供这些集成条件，不能假设外部系统可直接工作。

需要升级给教师的情况

出现以下情况应停止实验并报告教师，而不是继续加大推力或增益：

  • 模型能加载但持续穿透地面或出现极端数值；
  • ONNX 输入维度与 45 不符；
  • ROS2 消息中的 NaN/Inf 无法定位来源；
  • 有效命令在超时后仍出现异常大力矩；
  • 多发布者导致控制交错且无法确认唯一发布者；
  • WSL 图形环境或 ROS2 工作空间被破坏，需要系统级修复。

常见错误

  • 只背命令，不检查运行目录和环境：同一句命令在不同终端可能得到不同结果。
  • 把测试通过等同于所有实验通过：单元测试不覆盖 GUI、完整 ONNX 推理和 ROS2 通信。
  • 同时改变摩擦、重力和姿态：无法归因，实验结果不可复核。
  • 将设定速度当作真实测量速度：日志字段必须结合代码来源解释。
  • 用真值里程计冒充 SLAM 估计：违反课程边界，也不能用于证明算法效果。
  • 忽略非法消息不刷新时间戳：会误判 0.5 秒超时行为。
  • 将零力矩理解为安全站姿：它只是停止主动施力，重力仍可能使机器人倒下。
  • 在没有保存日志前反复重启：丢失故障现场，导致无法比较。
  • 直接修改课程源码来“修环境”：应优先恢复依赖、资源、工作空间和 source 顺序。
  • 验收记录只写截图不写条件：至少应记录脚本、初始状态、改变量和复位步骤。
